# ADR 0036 - Guarded PySAML2 MD5 EPTID compatibility

- **Status:** Accepted
- **Date:** 2026-07-06
- **Deciders:** gamlastan maintainers
- **Supersedes in part:** [0008](0008-idp-server-infrastructure.md)
- **Implementation:** `crates/gamlastan/src/idp/eptid.rs`, workspace `Cargo.toml`

## Context

ADR 0008 deliberately diverged from PySAML2's stock `saml2.eptid.Eptid` by
using SHA-256 for newly generated `eduPersonTargetedID` values. That remains the
right default for new gamlastan deployments.

During SATOSA/PySAML2 migration work, we found a narrower compatibility need:
some SPs may already store the PySAML2-generated EPTID, or a persistent NameID
derived from that value, as the user's account key. For those SPs, changing the
hash algorithm changes the user identifier and can strand existing accounts even
when the IdP entityID, SP entityID, user identifier, and secret are otherwise
unchanged.

The PySAML2 stock formula is:

```text
idp_entity_id + "!" + sp_entity_id + "!" + md5(user_id || sp_entity_id || secret)
```

Importing old mappings remains the safest migration path when values were
hand-edited, imported, normalized differently, or generated by custom code. But
when the old deployment used the stock PySAML2 formula and the inputs are known,
recomputing the legacy value is useful for controlled cutovers.

## Decision

Add an explicit compatibility mode to `gamlastan::idp::eptid`:

- Keep SHA-256 as the default `Eptid` digest. Existing constructors (`new` and
  `with_store`) continue to use SHA-256 and preserve current behavior.
- Add `EptidDigest::Pysaml2Md5Legacy` and `EptidOptions` for callers that need
  legacy PySAML2 parity.
- Require `allow_legacy_md5 = true` when the legacy digest is selected. Fallible
  constructors reject MD5 compatibility unless that guard is set.
- Compute the PySAML2-compatible value exactly as
  `idp!sp!md5(user_id || sp_entity_id || secret)`.
- Keep the mode in the EPTID helper only. Higher-level applications decide
  whether to expose it, how to scope it per SP, and when to retire it.

## Security Boundaries

| Threat | Control | Residual risk |
| --- | --- | --- |
| Accidental weak digest use | MD5 is unreachable through existing constructors and requires `allow_legacy_md5 = true` | A caller can still deliberately enable it too broadly |
| Identifier mismatch during migration | The legacy formula matches stock PySAML2 when inputs and secret match | Custom stores, changed normalization, or hand-edited values still require importing old mappings |
| New deployments depending on MD5 | Documentation and API names mark this as legacy compatibility, not the default profile | Downstream configuration must scope and retire the compatibility mode |

## Consequences

- gamlastan can support cutovers for SPs whose account key is a stock PySAML2
  MD5 EPTID without changing the secure default for new identifiers.
- Existing SHA-256 EPTID values are unchanged.
- Callers that need legacy values must opt into a fallible constructor and pass
  an explicit guard. This makes the compatibility decision visible in code and
  configuration review.
- The earlier ADR 0008 rejection of MD5 remains true for the default profile,
  but is superseded for this explicit migration mode.
